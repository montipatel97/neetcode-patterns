# NeetCode 150 — Patterns, Proofs & Traces

A static site built from the *Algorithm Pattern Reference* PDF. All **18 roadmap topics** are complete:
seven sections each, **54 animated dry runs** driven by real execution traces, a pattern-recognition
quiz per topic, and a checklist over all **146 practice problems**.

## Running it

Open `index.html` — no build step, no install, works offline. Everything loads via plain `<script>`
tags rather than `fetch()`, specifically so that `file://` works by double-click.

To serve it over HTTP instead:

```bash
python -m http.server 4173
```

It's a folder of static files, so it drops straight onto GitHub Pages / Netlify with no config.

## Publishing to GitHub Pages

The site is plain static files with only relative paths, so it works unchanged at a project-page
subpath like `your-username.github.io/neetcode-patterns/`. `.nojekyll` is present so Pages serves the
tree as-is instead of running Jekyll over it.

```bash
gh repo create neetcode-patterns --public --source=. --remote=origin --push
```

Then turn on Pages (branch `main`, folder `/root`):

```bash
gh api -X POST repos/:owner/neetcode-patterns/pages -f source[branch]=main -f source[path]=/
```

## How the dry runs work

The trace tables in the source PDF do not survive text extraction — the columns interleave, so several
of them read as scrambled nonsense. Rather than transcribe them by hand, every trace here is
**generated by executing the code**.

`tools/tracer.py` runs each solution under `sys.settrace` and records a deep-copied, JSON-safe snapshot
of every watched local at every line event. The player in the browser replays those snapshots.
Consequences worth knowing:

- Every value shown is what Python really produced — 3118 traced steps across the 54 examples.
- A snapshot holds the state *before* its line runs, so stepping forward shows the effect of the line
  you just left. The "changed" strip under the panes is a diff against the previous step.
- Nested recursive helpers are traced too (`diameter`'s inner `height`, backtracking's `dfs`), so the
  recursion itself is visible. Comprehensions and generator expressions are skipped as noise; an
  example can narrow this further with `"only": [...]`.
- Linked lists and trees get special handling. Their nodes are mutated in place, so snapshotting "the
  list reachable from head" would lose the picture. Instead every node is enumerated once, held at a
  fixed position, and only the **edges** are re-recorded per step — which is what makes a reversal
  legible as arrows flipping from forward to backward.

Regenerate everything, or one topic:

```bash
python tools/build_all.py
```

```bash
python tools/build_all.py trees
```

`python tools/check.py` prints every example's return value for spot-checking against the PDF.

## Layout

```
index.html                     page shell; hash router entry point
assets/css/style.css           all styling; per-topic accent via [data-accent]
assets/js/app.js               router, renderer, dry-run player, quiz, progress
data/roadmap.js                18 topics, master bounds table, Python hot paths
data/topics/<id>.content.js    topic prose: mechanics, proofs, rules, edges, bugs, quiz
data/topics/<id>.traces.js     GENERATED — do not hand-edit
tools/tracer.py                sys.settrace instrumentation + structure serialisation
tools/common.py                node classes, tree/list builders, output paths
tools/topics/<name>.py         the three worked examples per topic
tools/build_all.py             regenerates every trace bundle
tools/check.py                 prints each example's result
```

Topics are lazy-loaded: clicking one in the sidebar injects just that topic's two scripts, so the
first paint stays small and switching is instant. Script injection (unlike `fetch`) works on `file://`.

## Visualisers

The `view` block in each example picks how state is drawn. Available kinds:

| Kind | Draws | Used by |
| --- | --- | --- |
| `arrays` + `pointers` | cells with pointer flags, write highlights, window shading | most topics |
| `grids` | 2-D matrix with a focused cell | DP tables, grid DFS, matrix rotation |
| `stacks` | horizontal stack, top marked | stack, heap, backtracking path |
| `deques` | both ends marked | monotonic deque, BFS queue |
| `linked` | fixed nodes, SVG arcs for edges (backward = dashed amber) | linked list |
| `tree` | laid-out binary tree with SVG edges | trees |
| `tries` | nested-dict outline, current prefix highlighted | tries |
| `maps` / `sets` | key-value chips, membership tokens | hashing, graphs |
| `bits` | binary row with set bits lit | bit manipulation |
| `scalars` | changed values flagged amber | everywhere |

## Notes on fidelity

Two kinds of table in the PDF have their columns offset by one row in the text layer — the master
complexity table and the per-topic practice lists. Both were realigned by matching each phrase to the
row it describes (e.g. *"each element pushed and popped once"* belongs to Stack, not Two Pointers).
The reconstruction is in `data/roadmap.js` and in each topic's `practice` block.

Where a trace's output depends on something the problem leaves unspecified, the takeaway says so
rather than quoting one ordering as canonical:

- **Word Search II** emits words in DFS order, not input order.
- **Longest Consecutive Sequence** iterates a set; CPython happens to yield the sample input in
  ascending order, and the answer is order-independent anyway.
- **Number of Islands** uses a 3×3 grid of its own, not the PDF's example.

Everything else matches the PDF's stated outputs.
